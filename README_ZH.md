## 为什么做这个

每次收藏一篇新文章时，我脑子里都会闪过一个问题：下一次再打开它，会是什么时候？如果未来某一刻我真的需要它，我还能想起它曾经被放在这里吗？这个短暂的停顿有时会让我有点沮丧，因为我不确定眼前这些收藏、剪藏和整理，最后是不是真的会产生价值。

所以，当我第一次看到 Karpathy 提出 LLM Wiki 的概念时，第一反应就是把它用到个人知识管理里。

坦白说，这套框架并不适合所有场景。它不是最高效的检索系统，也不适合直接承担企业数据库、学术文献库这类大规模信息检索任务。在那些场景里，RAG 往往仍然是更优解。但如果从个人知识管理出发，问题就不一样了。

我的目标不是让系统最快地找出某个答案，而是让那些零散读过的文章、笔记和想法，在未来有机会连点成线，逐渐构建出我对某个主题的真实认知。原始信息不应该只是安静地躺在文件夹里，等待某一天被偶然调用。更理想的状态是：**它们持续产生新的连接，慢慢形成对某个主题更深入的理解。**

llm-wiki-stack 不解决收藏或检索的挑战，而是为信息合成给出一个方向。

## 适合谁

- 经常收藏文章、播客、访谈、报告，但很少真正复用的人
- 用 Obsidian、Markdown 或文件夹管理个人知识库的人
- 想把阅读材料沉淀成概念网络，而不只是全文搜索结果的人
- 愿意让 LLM 做整理、链接和体检，但自己保留判断权的人

它不适合需要企业级大规模检索的人，也不适合想要完整 GUI 产品的人。它更像一套轻量工作流：文件夹、Markdown、Obsidian，再加上几个 LLM 命令。

## 快速开始

```bash
npx llm-wiki-stack
```

这会把四个命令安装到 `~/.claude/skills/`。然后在你的 Obsidian 仓库中打开 Claude Code：

1. **仅一次**：`/kb-init` — 初始化三层知识库结构
2. **日常**：`/wiki-compile` — 将新 raw 笔记编译为 wiki 概念页
3. **有疑问时**：`/wiki-topic` — 围绕一个问题，从你自己的笔记中生成结构化分析
4. **隔一段时间**：`/wiki-lint` — 做一次知识库体检：断链、孤岛概念、脆弱依赖、概念演化

试试这四个动作。你很快会知道它是不是适合你。

## 如何工作

把它看作知识的**编译器**：源素材进去，结构化的概念网络出来。

运行一段时间后，它长出来的不是文件夹里的文章列表，而是一张可以继续扩展的概念网络：

![Obsidian 图谱视图中的概念网络](assets/obsidian-graph.png)

```
01 raw/   ──编译──>  02 wiki/   ──对话──>  03 outputs/
(源笔记)             (概念网络)             (你的观点)
```

每层分工明确：

| 层 | 谁负责 | 做什么 |
|----|--------|--------|
| `01 raw/` | **你** | 存文章、剪藏、想法。LLM 只读正文，不改写原文。 |
| `02 wiki/` | **LLM** | 提取对象和概念，追踪理解演变，建立双向链接。 |
| `03 outputs/` | **你 + LLM** | 你提问，LLM 揭示结构化关系，你写下结论。 |

结果是：每个概念有一页，每页链接到出处，每条出处可追溯，每次理解的改变都记录下来。

## 一个实际流程

你把十几篇关于“长期主义”的文章放进 `01 raw/`。

运行 `/wiki-compile` 后，系统不会只生成摘要，而是提取出“延迟满足”“复利效应”“路径依赖”“身份叙事”等对象和概念页，并把它们链接回原文。

几周后，你问 `/wiki-topic`：

> 长期主义什么时候会变成自我欺骗？

系统会从你的材料里找出概念之间的张力、冲突和类比，生成一份结构化分析。最后的判断仍然由你来写。

这就是这套系统的价值：过去积累的材料，不再只是被保存，而是重新参与思考。

## 命令

| 命令 | 角色 | 做什么 |
|------|------|--------|
| `/kb-init` | 架构师 | 初始化三层结构，生成 `AGENTS.md`，编译存量 raw。 |
| `/wiki-compile` | 编译器 | 从新 raw 中提取对象和概念，执行索引边界检查，建立交叉引用。 |
| `/wiki-topic` | 分析师 | 基于问题合成观点：揭示因果链、矛盾张力、类比映射、合成假设。 |
| `/wiki-lint` | 审计师 | 月度体检：断链、孤儿页、脆弱依赖、概念演化一览。 |

## 让它运转的核心机制

### 索引边界：可定义性 + 连接强度

这个项目最初看起来并不复杂。我只花了一上午就搭出了系统初版，毕竟它本质上只是一个 skill。后续真正耗时的部分，花在了“如何让大模型构建索引”上。

一开始，我几乎完全相信模型的能力，让它自由构建索引。结果很快发现，生成出来的概念很难继续使用，而且大量素材被遗漏在索引之外。

调试过程经历过一个从膨胀到收缩的过程。我最初的思路是发现一个问题，就加一条限制。后来限制越加越多，但效果并没有稳定变好。改了很多版之后，我意识到这种方式没有尽头，于是决定推翻重来，从目标本身重新审视索引的构建逻辑。

最后，我把索引标准收敛成两个问题：

- **可定义性**：这个索引是否有明确、稳定、不容易产生歧义的定义？它用来避免索引过度泛化，或者把太多不同内容塞进同一个概念里。
- **连接强度**：这个索引能连接多少原始素材？它用来避免创建大量只服务于单篇文章、无法在未来继续复用的一次性概念。

具体执行时，每个新概念都必须先“挣到”自己的页面：能清楚定义，拥有单一核心，并且能从多个来源中获得支撑。其他更主观的判断，比如索引健康度、内容深度、形成话题的潜力，则交给 `/wiki-lint` 给出建议，但不替你决定某个索引是否应该保留或创建。

### 概念演化：永不覆盖

新信息默认**追加**。只有新证据**明确纠正**了旧事实错误时，才更新核心定义，并把旧理解归档到“概念演化”区，附上时间和出处。

观点冲突不会被强行合并，而是并列记录在“不同理解”区。你的思想史被保留，不被抹去。

### 交叉引用完整性

每条关键陈述链接到 raw 出处。每个 wiki 链接保持双向。每次编译都会验证 `linked_count`，断链和孤岛概念会在体检报告中浮出来。

没有隐藏状态，也没有黑盒数据库。一切都是带 YAML frontmatter 的 Markdown 文件。

### 人判断，LLM 编译

LLM 负责整理、链接、补全元数据、发现结构问题；你负责判断、取舍、追问和最终观点。

这也是我刻意没有设计 GUI 的原因。一方面，Obsidian 是天然的可视化展示端。而另一方面，即使你不用 Obsidian，只用文件夹和 Markdown 管理，也完全可以运行这套系统。

个人知识库最重要的是里面的内容，而不是操作界面本身。文件夹仍然是最自由、最灵活的形态。你也可以在这个版本上继续修改，找到最适合自己的产品形态。

## 结语

乔布斯在斯坦福毕业典礼演讲中，除了那句著名的 “stay hungry, stay foolish”，还讲过另一个概念：connecting the dots。我很喜欢。他把人生经历比作一系列的点，只有回头看时才能发现它们之间的联系。我们每个人都在不断收集这些点：读过的文章、听过的讲座、经历过的事件、产生过的想法。它们散落在记忆里，或者保存在某个文件夹里，但它们真正的价值在于它们之间的连接。

我也希望这套系统能帮你把散落在人生旅途中的点滴认知连接起来，让你的过去滋养你的未来。
